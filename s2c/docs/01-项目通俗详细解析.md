## 一、 项目是做什么的？（项目背景与目标）

本项目的全称是 **HiLSA-MoE** (Hierarchical Intent Localization and Semantic Analysis - Mixture of Experts)。它主要解决的是自然语言处理（NLP）对话系统中的**开放意图识别（Open Intent Recognition, OIR）**问题。

**通俗来说：**
当用户对语音助手或聊天机器人说话时，系统需要知道用户想干什么（意图识别）。如果用户问的是系统“已支持的业务”（称为已知意图，ID - In Domain），系统需要精确分类并处理；但如果用户问的是系统“不支持的业务”或在胡言乱语（称为领域外意图，OOS - Out of Scope），系统必须能**安全地拒绝**，而不是强行给出一个错误的回答。

这个项目就是要构建一个**高准确率、防误判、模块化**的全链路推理系统。

---

## 二、 整体架构是如何设计的？

项目摒弃了“一个大模型解决所有问题”的粗暴做法，而是设计了一个像“漏斗”一样的**三级级联架构**：**Gate（网关） -> Router（路由） -> Expert（专家）**。

这种设计的逻辑与我们在大公司办事的流程非常像：
1. **Gate（保安）**：负责在大门口识别你是不是来办正事的。如果是捣乱的（OOS），直接请出去；如果是合法客户（ID），放行。
2. **Router（前台引导员）**：合法客户进入大厅后，前台将你引导到具体的大类业务区（比如去理财区还是去贷款区）。
3. **Expert（具体业务专员）**：业务区的专员最终为你办理非常具体的业务（比如“开通信用卡”）。

这种架构的好处是：**各司其职，互不干扰**。拦垃圾数据的事专心交给 Gate 做，后面的 Router 和 Expert 就可以假设自己面对的永远是干净的合法数据，从而极大地提升了分类的准确率和训练的效率。

## 三、 数据集介绍与极其严格的处理逻辑

数据是驱动这个系统运转的核心。项目中数据的拆分与构建有着非常严谨的逻辑（具体实现在 `scripts/data/active/rebuild_v19_2_strict.py` 等脚本中）。

### 3.1 数据集来源与 50% 已知意图比例设定（核心实验设置）
项目源数据主要基于 **CLINC150 (clinc_data_origin)** 数据集。这个经典数据集原本包含了 150 个日常对话意图，以及一部分官方提供的 OOS（领域外）查询数据。

**关键实验设置：**为了模拟真实的“开放世界”场景，充分验证系统拦截未知意图的能力，我们的实验严格按照 **“已知意图比例 50%” (Known Intent Ratio = 50%)** 的设定进行。
也就是说，我们将原本的 150 个意图硬性一分为二：
*   **保留 75 个作为“已知意图”（Known Intents，ID）**：划分到 10 个大领域（Domain）中，我们的系统（特别是 Router 和 Expert）只负责学习和处理这 75 个意图。
*   **另外 75 个作为“未知意图”（Unknown Intents，OOS）**：这些意图完全向系统保密，并与官方原有的 OOS 数据混合在一起。在测试阶段，它们会作为“干扰项”疯狂进入系统，专门用来考验 Gate（网关）能否成功识别并拦截它们。

### 3.2 严格的数据切分与构建逻辑
为了让“保安、前台、专员”各司其职，项目对训练和测试数据进行了**极其严苛的物理隔离切分**：

*   **针对 Gate（网关）：**
    *   **训练集**：**100% 只有已知意图（Known only）**。为什么？因为在真实世界中，你永远无法穷尽未知的 OOS 垃圾话。所以 Gate 的训练逻辑是“学会认识正常的请求长什么样，画个圈，圈外的全是异常”。
    *   **验证集与测试集**：包含 已知意图 + 未知 OOS 数据。用来测试 Gate 能不能成功放行正常请求，并把奇怪的请求拦住。
*   **针对 Router 和 Expert（路由与专家）：**
    *   **训练集、验证集、测试集**：**全都是已知意图（Known only，闭集假设）**。
    *   因为设计上假设了 Gate 会百分之百把 OOS 拦在门外，所以后置的组件在训练和测试时，根本不需要、也不能去接触 OOS 数据，避免受到噪声污染。

## 四、 核心组件详解（模型与实现策略）

这是系统中最重要的三个齿轮，每个组件都选用了最适合自己生存环境的 AI 模型和算法。

### 4.1 Gate（网关 - 领域外检测器 OOS Detector）
**主要职责**：区分 ID（合法）和 OOS（不合法）。
*   **所用模型**：`all-MiniLM-L6-v2`。这是一个极其轻量级但非常强大的句向量（Embedding）模型。它只有 22M 参数，速度极快，适合做第一道关卡。
*   **实现策略原理 (MultiSphere / MultiPrototype)**：
    1.  **特征提取**：利用 MiniLM 模型，把用户输入的每一句话变成一个 384 维的数值向量。
    2.  **画圈圈（聚类构建 Sphere）**：在训练阶段，算法把所有合法的已知意图向量绘制在多维空间中，并使用 K-Means 算法找到每个意图的高密度中心点，然后基于这些点最远的合理距离，画出一个“安全半径（Radius）”。这就是“多球体边界”概念。
    3.  **拒识判定**：在真实推理（测试）时，新的一句话进来，同样变成向量。算一下它离所有合法意图中心的距离：如果它落在了任何一个“安全球体”内部（距离 < 半径 + 容忍阈值 margin），就算合法请求（ID），放行。如果离所有的合法球体都非常遥远，说明这是个没见过的异类，直接拒绝（识别为 OOS）。
    4.  **后置验证 (Semantic Verifier)**：对于拿捏不准的擦边球请求，系统还配备了 `IntentPrototypeMatcher`（意图原型匹配器）甚至 LLM 来做二次人工查验，兜底安全性。

### 4.2 Router（路由 - 领域分类器）
**主要职责**：把合法的请求分配到 10 个特定的超管领域（如 银行业务、差旅业务 等）。
*   **所用模型**：`SmolLM-135M` + LoRA 微调。这是一个小参数量的 Decoder-only （类 GPT）架构大语言模型。
*   **实现策略原理**：
    1.  **接受干净数据**：Router 放心地接收 Gate 传过来的合法句子。
    2.  **序列分类（Sequence Classification）**：这并不是让 LLM 去续写文字，而是利用 `SmolLM135M` 优秀的语义理解能力，并在其顶层加了一个分类头。整个网络通过 Low-Rank Adaptation (LoRA) 技术进行高效微调，使其专门适应“领域分类”任务。
    3.  **分发**：直接输出对应领域的标签 ID。

### 4.3 Expert（专家 - 细粒度意图分类器）
**主要职责**：在特定领域下，精准打到 75 个具体意图的一个。
*   **所用模型**：也是 `SmolLM-135M` + LoRA 微调架构（这表明系统大量复用了小模型架构来节约显存和时间）。根据系统配置，这可能是一个全知的大专家，也可能是每个大领域有自己特定的模型权重。
*   **实现策略原理**：
    与 Router 类似，也是利用基于 LoRA 的小大语言模型做极致的闭集细分分类。它的分类目标数量更多（75个意图），但因为它已经提前知道这句话属于哪个领域（比如已经确定是银行业务了，就不会再去和定外卖的意图搞混），所以准确率极高（通常在 93%+ 以上）。

## 五、 系统的全链路执行流（沙盘推演）

为了让你更直观地理解代码 `src/pipeline/system_pipeline.py` 是怎么运行的，我们模拟两个用户对话：

### 场景 A：用户说 "I want to apply for a new credit card" (合法请求)
1.  **进入 Gate**：MiniLM 模型将其转为向量，探测器发现这个向量完美落在了预先画好的“信用卡业务”聚类球体内部，距离极近。**状态：[Accept, 判定为 ID]**。
2.  **进入 Router**：SmolLM135M （Router 版）吞下这句话，通过分类层发现它的语义特征属于 `D_Banking`（银行业务类型）。**状态：[Routed to Banking]**。
3.  **进入 Expert**：SmolLM135M （Expert 版，专注于银行方向）吞下这句话，结合上下文词汇，确定其细分标签确切为 `order_new_card`。
4.  **最终输出**：`Intent: order_new_card`（成功识别）。

### 场景 B：用户说 "How many stars are there in the universe?" (非法/瞎扯请求)
1.  **进入 Gate**：MiniLM 将其转为向量，探测器在多维空间一算，发现这个向量无论是离“订餐”、“银行”还是“打车”球体都十万八千里。完全溢出了预设的已知半径（Radius）。
2.  **拦截**：无需经过强大的 Router 和 Expert 大脑，Gate 直接切断通道。**状态：[Reject, 判定为 OOS]**。
3.  **最终输出**：`Intent: OOS`（安全拒绝，回答不在服务范围内）。

## 六、 总结与优势

HiLSA-MoE 的核心命题就是**“先排雷，再办事”**及**“专业模型干专业事”**：
*   **轻量化排雷**：第一级的 Gate 使用只有 22M 参数的模型排雷，算力开销极小。
*   **深层次理解**：后面的 Router 和 Expert 用 135M 参数的 SmolLM 配合 LoRA 去理解语言深层含义，保证了极高的准确性。
*   **模块解耦**：这种架构使得每次新增意图或业务领域时，只需要扩展部分专家（Expert）的知识和 Gate 的球体参数即可，维护起来非常清爽。
