# 项目阅读指南：从看懂到复现实验

如果你第一次打开 s2c，不要从 `docs/` 全部文件或 `tools/` 全部脚本开始。按本指南走，先建立运行模型，再看研究结果。

> **当前边界**：默认只在 `main` 工作树上阅读和运行。`../artifacts` 是跨分支保留的证据目录；其中的
> 结果必须通过 manifest 核对来源。不要切换、提交或推送 `autoresearch`；若旧 manifest 记录了该分支，
> 只把它当作结果 provenance。

## 0. 先记住四个目录

```text
src/       模型和可复用逻辑
tools/     一次性训练、评估和实验编排
tests/     协议约束，先读它能避免误用脚本
docs/      入口说明和历史背景
```

大数据不在仓库：

```text
../assets/       数据、MiniLM、SmolLM
../artifacts/    detector、checkpoint、CSV、Parquet、图
```

因此 Git 里看不到模型或完整预测文件是正常的；真正的结果来源必须通过 manifest 指向工作区产物。

## 1. 先读哪些文件

推荐顺序只有五个文件：

1. `README.md`：项目边界和当前主线；
2. `docs/PROJECT.md`：当前运行契约和证据优先级；
3. 本文件：如何从源码、数据、产物一路走通；
4. `docs/07-当前状态与里程碑.md`：已经完成和不能外推的结论；
5. `docs/EXPERIMENTS.md`：实验目录与指标读取方法。

再按需要查：

```text
docs/03-数据协议与版本.md   split、KIR、seed、OOS定义
docs/04-训练与评估流程.md   主训练和评价流程
docs/10-工具入口索引.md     命令行入口

```

编号为 `01/02/05/08/09/12/13/14` 的文档主要是背景、历史计划或旧实现解释。它们仍保留用于追溯，但不作为“今天应该运行什么”的依据。

## 2. 从一条样本理解代码

主调用关系如下：

```text
tools/eval/eval_system_pipeline_v19.py
    ↓ 创建 PipelinePaths
src/pipeline/system_pipeline.py
    ├─ _load_gate()
    ├─ _gate_predict()
    ├─ _router_predict()
    └─ _expert_predict_group()
```

### Gate

`src/gate/multi_sphere_oos_detector.py` 负责：

- 读取 MiniLM embedding；
- 找到最近的 Known intent/cluster；
- 计算距离、半径和 OOS 分数；
- 输出 `pred=1` 时拒绝为 OOS。

Gate 不负责最终 intent 分类。查看 `nearest_intent` 只能用于诊断，不能把它当作 Expert 预测。

### Router

`src/router/` 加载 SmolLM+LoRA domain 分类器。它只回答“应该进入哪个 domain”。单 domain 数据集的 Router 近似 identity，但仍需要检查 checkpoint 和 label map。

### Expert

`src/models/expert.py` 中的 `SmolLMExpert` 负责域内意图分类，
`src/inference/expert_manager.py` 负责推理时复用基础模型并切换 LoRA adapter；
`tools/train/train_expert_v19.py`/`train_all_experts_v19.py` 负责训练并保存 `best_model.pt`。
它回答“在该 domain 内是哪一个 intent”。不要把 `src/router/router_model.py` 的 Router 输出当成 Expert 结果。

### 样本级错误

评价脚本会在 predictions 中写入：

```text
correct_oos_rejection
oos_accepted_by_gate
known_rejected_by_gate
known_wrong_domain
known_wrong_expert
correct_known_prediction
```

先看错误阶段，再看总 F1。这样才能判断是 Gate 研究问题，还是下游模型训练问题。

## 3. 当前研究主线怎么读

研究问题不是“哪个 K 最大”，而是：

```text
MiniLM 表示
  → Known 是否形成局部多簇
  → 多簇边界是否覆盖 Known、拒绝 OOS
  → near-OOS 的碰撞发生在表示层还是边界层
  → Gate 改善能否传递到 Cascade
```

### Gate-only 结果

先看：

```text
../artifacts/s2c/outputs/experiments/cluster_separability_v19/
../artifacts/s2c/outputs/experiments/cluster_separability_v20/
../artifacts/s2c/outputs/experiments/cluster_separability_v21/
../artifacts/s2c/outputs/experiments/minilm_representation_analysis/
```

主结论的正确表述是：多簇是条件性收益；BANKING77-OOS 更可能受益，StackOverflow 的固定多球会退化，near-OOS 常见表示碰撞。不要写成多簇普遍提升。

### 完整 Cascade 结果

本轮修复后的入口和结果是：

```text
tools/eval/run_cascade_repair.py
../artifacts/s2c/outputs/experiments/cascade_repair/gpu_kir50_seed42/
```

四个 Gate 只在相同下游组件上比较。先打开 `evaluations/matrix_manifest.json`，再逐个打开每个 Gate 的 `eval_results.json` 和 `predictions.json`。

完整系统矩阵入口是（当前已完成的 KIR50 扩展流程）：

```text
tools/train/run_cascade_components.py
tools/eval/prepare_cascade_gates.py
tools/eval/run_cascade_matrix.py
../artifacts/s2c/outputs/experiments/cascade_full/gpu_kir50/
```

它固定 KIR50、seed13/42/87 和四个 Gate，共 36 个单元；当前矩阵已完成。先看
`cascade_full/gpu_kir50/evaluations/matrix_manifest.json`，确认 `status=complete`
和 `completed_unit_count=36`，再读 `cascade_summary.csv`。KIR25/75 暂不纳入这张四
Gate 表，因为当前 CE-Recon 表示 checkpoint 没有覆盖这些 KIR。

## 4. 一个完整实验单元的检查清单

打开任一单元后，依次核对：

```text
[ ] dataset / kir / seed 正确
[ ] data_root 指向 prepared/multidataset/v19
[ ] Gate detector 和 encoder 是同一表示空间
[ ] CE-Recon 单元加载了 encoder.pt
[ ] Router checkpoint 没有随 Gate 改变
[ ] Expert root 是修复后的目录，而不是旧 smoke
[ ] 阈值和 selected K 来源于 validation
[ ] eval_results.json 有 OOS、Known 和 overall 指标
[ ] predictions.json 有 error_stage
```

任一项不满足，都只能把结果标成诊断或 smoke，不能作为公平主表。

当前 full matrix 的推荐最短核验路径是：

```text
../artifacts/s2c/outputs/experiments/cascade_full/gpu_kir50/evaluations/matrix_manifest.json
  → ../artifacts/s2c/outputs/experiments/cascade_full/gpu_kir50/cascade_summary.csv
  → 任一 Gate 目录下的 eval_results.json
  → 同目录 predictions.json（只查具体错误）
```

## 5. 典型命令

```bash
# 只看当前入口
python -m src.cli --help
python -m tools.experiments.cluster_separability --help

# 数据准备 dry-run
python -m src.cli prepare --dataset clinc150 --kir 50 --seed 42 --dry-run

# 检查完整 Cascade 的文件是否齐全（默认只做 preflight）
python tools/eval/run_cascade_repair.py

# 运行 unit tests
pytest tests/unit -q
```

GPU 训练/评价需要在 `bo` 环境中运行。不要在没有设置 CUDA 动态库路径时，把“找不到 libcusparseLt”误判成代码错误；先看终端中实际使用的 Python、torch 版本和 `nvidia-smi`。

## 6. 修改代码时的最小原则

- 先读 `tests/unit/` 中对应协议测试；
- 复用 `WorkspacePaths`、现有 evaluator 和 detector，不复制一套平行实现；
- 新实验使用新的结果目录，不覆盖 `paper_results`、历史 detector 或 checkpoint；
- 新增入口使用功能名（如 `run_cascade_repair.py`），不要再创建 `v24/v25` 文档和 CLI；
- 每个新字段都要在 manifest 中写清来源；
- 代码注释解释“为什么不能换”，不要重复描述显而易见的语法。

## 8. 一条结果的最小核验路径

如果只想复核一张论文表，不要遍历所有预测文件：

```text
实验目录
  → run_manifest.json / matrix_manifest.json
  → 汇总 CSV
  → paper_source_map.csv（若属于论文收口）
  → scores.parquet 或 predictions.json（只查异常样本）
```

若 manifest 中的 `source_commit`、数据 hash、阈值选择集或模型路径缺失，这条结果只能标为
诊断/历史结果，不能直接写成当前 `main` 的可复现数字。
