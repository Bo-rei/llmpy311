## 1. 项目定位

s2c 是一个面向**开放意图识别**（open intent recognition）的分层系统。它不是一个单点分类器，
而是一条明确的级联链路：

1. **Gate**：先判断输入是已知意图（ID）还是未知意图 / OOS（out-of-scope）。
2. **Router**：对通过 Gate 的 ID 样本预测域（domain）。
3. **Expert**：在目标域内做细粒度意图分类。

项目的中心目标不是“把单模型 accuracy 拉到最高”，而是同时平衡：

- OOS 拒识能力。
- 已知意图识别准确率。
- 端到端 Macro-F1。
- 整个推理链路是否可解释、可调试、可复现。

从仓库的文档与实现看，当前主线已经非常明确：**先拒识，再路由，最后分类**。

## 4. 总体系统：Gate -> Router -> Expert

### 4.1 推理主链路

`src/pipeline/system_pipeline.py` 中的 `HiLSAMoEV19Pipeline` 是整个系统的统一推理入口。它负责：

1. 加载 Gate 编码器和 OOS 检测器。
2. 加载 Router 及其标签映射。
3. 索引各域 Expert。
4. 构建 intent prototypes。
5. 可选启用语义 gate / verifier。

在运行时，主流程是：

```text
text -> gate encoder -> OOS decision
     -> if ID: router -> domain
     -> domain expert -> fine-grained intent
```

### 4.2 关键路径

- `predict_one()` / `predict_batch()` 是系统级推理入口。
- `gate_mode` 控制 OOS 主机制：`multisphere`（默认）或 `multi_prototype`。
- `semantic_gate_enabled` 控制是否启用第二阶段语义校验。
- `semantic_gate_mode` 支持 `prototype`、`llm_verifier`、`fusion`。
- `semantic_gate_mode=llm_verifier` 时，Gate 会对不确定样本做 SmolLM 语义复核；`fusion` 则融合 prototype 分数与 LLM 分数。

### 4.3 负责任务拆分

这个系统的设计原则非常明确：

- Gate 只负责**是否拒识**。
- Gate 的二次兜底由 SmolLM semantic verifier 处理不确定样本。
- Router 只负责**去哪一个域**。
- Expert 只负责**域内细粒度分类**。

这也是后续 Method 写作时最该保留的叙述骨架。

## 5. Gate：嵌入、对比学习、多中心结构与 OOS 检测

Gate 不是单一函数，而是一组互补模块：

1. 文本嵌入器。
2. 对比学习投影头。
3. 多中心 prototype / cluster 结构。
4. 多超球 OOS 检测器。
5. 可选的语义校验与融合。

### 5.1 文本嵌入

`src/gate/intent_prototype_matcher.py` 和 `src/gate/contrastive_intent_encoder.py` 都使用了相同的基本编码方式：

- tokenizer 截断到 `max_length=64` 或配置值。
- backbone 输出最后一层 hidden states。
- 使用 attention mask 做 mean pooling。
- 对 pooled 表示做 `L2` 归一化。

可写成：

\[
e = \mathrm{Norm}\left(\frac{\sum_t m_t h_t}{\sum_t m_t}\right)
\]

其中 `h_t` 是 token hidden state，`m_t` 是 attention mask。

### 5.2 对比学习投影头

`ContrastiveIntentProjector` 的作用不是直接做分类，而是把 backbone 表示映射到更适合几何判别的空间。

它的结构是：

`Linear -> GELU -> LayerNorm -> Linear -> L2 normalize`

对应实现位于 `src/gate/contrastive_intent_encoder.py`。

同时，这个文件还定义了两类损失：

- `supervised_contrastive_loss()`：同类为正样本，不同类为负样本。
- `hard_negative_contrastive_loss()`：显式引入 hard negative。

这部分可以在 Method 中解释为：**先通过对比学习拉开已知意图的几何间隔，再在该表示空间上做 OOS 边界建模。**

### 5.3 多中心 prototype 结构

`src/gate/intent_prototype_matcher.py` 与 `src/gate/multi_prototype_gate.py` 都表明：

- 单个 intent 不一定只对应一个中心。
- 每个 intent 可以对应多个 prototype / center。
- prototype 数量可通过 `k_default`、`k_overrides` 或同类配置控制。

在代码中，prototype 生成方式是：

1. 收集同一 intent 的训练样本。
2. 对其 embedding 做 K-means。
3. 若 `k=1`，退化为类中心。
4. 若 `k>1`，形成多中心簇。

`configs/clustering.yaml` 中给出了该阶段常用的超参范围：

- `k_min: 8`
- `k_max: 20`
- `sample_rate: 0.5`
- `sample_cap: 10000`
- `metric: cosine`
- `recluster_epochs: [2, 12]`
- `lof.n_neighbors: 20`
- `lof.contamination: auto`

这些配置说明，当前项目并不把 intent 空间看成单峰分布，而是默认它存在局部多模态结构。

### 5.4 多中心距离门控：Multi-Sphere OOS Detector

`src/gate/multi_sphere_oos_detector.py` 是当前最核心的 OOS 几何门控实现。它的主思想是：

- 用多个超球覆盖 ID 支持集。
- 每个超球有一个中心和一个半径。
- 半径不用最大距离，而是用分位数统计，避免离群点把边界拉大。

#### 5.4.1 中心计算

代码支持三种中心模式：

- `kmeans`
- `class_centroid`
- `class_centroid_mixture`

其中，`class_centroid_mixture` 允许一个 intent 拆成多个子中心，适合做多中心分析。

#### 5.4.2 半径计算

对每个簇，先得到该簇内样本到中心的距离，再按统计规则估计半径：

\[
r_y^k = Q_q\left(\{\|e_i - c_y^k\|_2\}_{i \in \mathcal{S}_{y,k}}\right)
\]

其中 `Q_q` 是分位数，默认实现使用 `radius_quantile=0.95` 一类的配置。

除了 quantile，代码还支持：

- `mean_std`：均值 + 标准差。
- `mahalanobis_diag`：对角马氏距离。实现中每个局部簇使用其自身的 Known train 样本估计对角协方差（`covariance_scope=per_cluster`，`covariance_eps=1e-6`），不使用全局方差。

#### 5.4.3 判决规则

对于 query embedding `e`，先计算它到所有 sphere 的距离：

\[
d(e) = \min_{y,k} \|e - c_y^k\|_2
\]

如果最近球满足：

\[
\|e - c_y^k\|_2 \le r_y^k
\]

则判定为 ID；否则判定为 OOS。

同时，代码还保留了一个 margin 约束：最近球和次近球之间需要保持足够间隔，否则样本会被视为不稳定区域。`predict_with_scores()` 会返回：

- `pred`
- `score`
- `nearest_cluster`
- `distance`
- `radius`
- `margin_ok`

这里的 `score` 可理解为“越大越像 OOS”的连续分数。

#### 5.4.4 评估与阈值调优

该 detector 支持在 validation 集上调 `radius_quantile`，而不是直接在 test 上拟合。对应方法为：

- `evaluate()`：输出历史兼容的 ID recall、OOS rejection、F1-like。新的多簇实验不使用该 F1-like 选 K，而统一使用以 OOS 为正类的标准 OOS Precision/Recall/F1、AUROC、AUPR-OOS 与 FPR95。
- `tune_radius_quantile()`：在 Val 上搜索最优 quantile。

这点对论文写作很重要：**测试集不用于阈值拟合**。

### 5.5 多 prototype 门控

`src/gate/multi_prototype_gate.py` 是另一条已知意图边界建模路径。它的机制更偏向“相似度门控”而不是“超球拒识”：

- 每个 intent 可有多个 prototype。
- query embedding 与所有 prototype 做 cosine similarity。
- 对每个 intent 的多个 prototype 做聚合。

代码支持几种 score mode：

- `max`
- `top2_margin`
- `top2_margin_conf`

并支持一个三段式决策：

- `score >= tau_high`：accept
- `score < tau_low`：reject
- 介于两者之间：uncertain

这意味着项目实际上已经具备“二阈值不确定区”的实现基础，只是主线方法是否采用，要看最终论文叙述。

### 5.6 语义校验与双表示融合

当前 pipeline 还支持可选语义验证：

- `IntentPrototypeMatcher`：在 SmolLM embedding 空间中构建 intent prototype。
- `LLMSemanticVerifier`：对 uncertain 样本进行语义层面的 yes/no 判定。

系统还提供了 `dual_representation_gate.py`，把 fast gate score 和 semantic score 做线性融合：

\[
s_{fused} = \alpha s_{fast} + \beta s_{semantic}, \quad \alpha + \beta = 1
\]

不过要注意：**这个融合门控在当前主 pipeline 中是可选扩展，不应默认写成主方法**。主方法仍然应以 multi-sphere OOS gate 为核心。

## 6. Router：已知意图后的域路由

`src/router/router_model.py` 定义了 `QwenRouter` 和 `SmolLMRouter`。

### 6.1 模型结构

Router 的结构很标准：

1. 载入 causal LM backbone。
2. 加 LoRA（`q_proj`、`v_proj`）。
3. 对最后一层 hidden states 做 masked mean pooling。
4. 接一个线性分类头，输出 domain logits。

在 `SmolLMRouter` 中，对应代码是：

- `self.base = AutoModelForCausalLM.from_pretrained(...)`
- `get_peft_model(...)`
- `self.classifier = nn.Linear(hidden_size, num_classes)`

### 6.2 Router 的数学形式

可写成：

\[
p(d\mid x) = \mathrm{softmax}(W \cdot \mathrm{Pool}(h_{1:T}))
\]

其中 `Pool` 为 attention mask 加权 mean pooling。

### 6.3 写作上如何定位 Router

Router 不应被写成论文主角。它的作用是：

- 让 ID 样本进入正确 domain。
- 减少将来域内分类的搜索空间。
- 与 Gate 共同完成级联分流。

论文里可以只保留一小段说明其结构和职责，不需要像 Gate 那样展开太多。

## 7. Expert：域内细粒度意图分类

`src/models/expert.py` 定义了 `SmolLMExpert`，而 `src/inference/expert_manager.py` 负责域级专家管理。

### 7.1 Expert 模型结构

Expert 由三部分组成：

1. `AutoModelForCausalLM` backbone。
2. LoRA 微调层。
3. `ProjectionHead` 投影头。

前向过程是：

1. 对输入做 masked mean pooling。
2. 送入 projection head。
3. 输出 L2 归一化后的特征向量。

这意味着 Expert 更像“表示学习 + 最近中心 / 分类头”的混合结构，而不是单纯的语言模型生成头。

### 7.2 ExpertManager 的作用

`ExpertManager` 使用一个共享 base model，按域动态切换 LoRA adapter。每个域注册时会加载：

- `best_model.pt`
- `intent_centroids.npy`

然后在推理时：

1. 激活对应域的 adapter。
2. 用该域的 projection / head 做预测。
3. 用 centroid similarity 作为置信度。

代码还提供了可选 energy score：

\[
E(x) = -T \log \sum_j \exp(z_j / T)
\]

它可用于 OOD 诊断，但不是当前主线 Gate 的核心判决。

### 7.3 为什么这个设计重要

这个设计的核心优势是：

- 参数共享，节省显存。
- 域间隔离，减少互相干扰。
- 便于按 domain 单独训练、单独评估和单独替换。

对于论文 Method，可以把 Expert 概括为：**共享 backbone + 域专属 LoRA + 域专属分类头 / centroid。**

- Expert 按域训练和评估，便于复用和分拆。

## 11. 论文 Method 写作建议

如果后续要把本文改写成论文 Method，推荐保持如下叙述顺序：

### 11.1 先写级联框架

先定义：

- OOS 是 one-class / rejection 任务。
- 已知意图是多类分类任务。
- 这两类任务本身不同，因此需要分层架构。

### 11.2 再写表示学习

然后说明：

- 文本如何编码。
- 为什么 embedding 空间里会出现多中心簇。
- 为什么需要 prototype / multi-center 而不是单中心。

### 11.3 最后重点写 Gate

重点放在：

- 多中心距离。
- 超球边界。
- quantile 半径。
- uncertain 区域。

这部分应当是论文 Method 的核心。

### 11.4 Router / Expert 简写

Router 和 Expert 只需交代：

- Router 做 domain routing。
- Expert 做 domain-specific intent classification。
- 两者通过 LoRA + 共享 backbone 提高效率。

### 11.5 不建议单独展开的内容

除非论文篇幅和贡献点需要，否则下面内容不建议单独成节：

- 双表示融合 gate。
- LLM semantic verifier 细节。
- 过多的工程包装器路径。

它们可以作为补充实验或附录内容。
