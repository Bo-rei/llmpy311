# 脚本归档与活跃边界

本文件解决“这个脚本能不能直接用”的问题。脚本是否活跃，不由文件名中的 v19/v20/v21 决定，而由统一入口、当前分支和结果 manifest 共同决定。

## 1. 当前 main 的活跃边界

### 核心运行

- src/cli.py：唯一基础工作流入口；
- src/：Gate、Router、Expert、Pipeline 和运行时路径；
- scripts/data/active/：数据准备、重建和审计；
- tools/analysis/：v19 训练、评估、消融和导出；
- tools/eval/：系统评估；
- tools/experiments/cluster_separability/：main 已注册的 v19/v20/v21 研究入口；
- tools/compat/textoir/：TextOIR split、协议和结果导入。

### 本地研究历史分支才有的后续入口

本地分支 autoresearch/minilm-collision-20260718 额外包含 CE-Recon、边界形状、外部 hard-negative、代表性 Cascade、MOGB 审计和 closeout 工具。该分支不是远程交付入口；它们不能仅因为 ../artifacts 里有结果就被当作 main 的当前入口。

## 2. 结果与源码不是一一随分支切换

../artifacts/s2c/ 是忽略目录，结果跨分支保留。看到以下目录只能说明“结果曾经生成过”：

- cluster_separability_v19/
- cluster_separability_v20/
- cluster_separability_v21/
- minilm_semantic_collision_v22/
- minilm_representation_analysis/
- end_to_end_representative/
- external_validation/
- study_closeout/

要知道结果由什么生成，查看该目录的 run_manifest、matrix_manifest、source_commit 或 closeout inventory。不要从目录名猜当前源码状态。

## 3. 归档判定规则

满足以下任一情况时，脚本视为历史/归档候选：

1. 不再被 src.cli 或统一研究 CLI 注册；
2. 只能复现已冻结的旧结果，不能生成当前协议产物；
3. 依赖旧数据路径、旧模型锚点或已弃用的指标语义；
4. 结果 manifest 已明确标记为 historical。

候选脚本暂时不删除。先在本文件或对应 manifest 写清：

- 原脚本解决什么问题；
- 当前替代入口是什么；
- 哪些历史结果仍依赖它；
- 如何进行最小 smoke 验证。

## 4. 当前不要做的清理

- 不要在实验数字冻结前批量移动 v20/v21/v22 脚本；
- 不要删除历史入口来“减少文件数量”；
- 不要把研究分支文件直接复制到 main，造成两套同名实现；
- 不要把 __pycache__、模型、Parquet 和大 CSV 当作源码入口；
- 不要修改历史 manifest 中登记的路径。

## 5. 建议的最终收口方式

等论文主表、Cascade、外部 hard-negative 和 MOGB 状态冻结后，再做一次小范围整理：

~~~
tools/experiments/cluster_separability/
├── active/   当前统一研究入口
├── legacy/   仅供历史复现的旧脚本
└── __main__.py
~~~

这一步必须保留兼容 wrapper，并先运行回归测试；当前阶段只更新文档，不执行目录迁移。

## 6. 如何追一条实验

~~~
结果文件
  → closeout/result_inventory.csv
  → source_commit / git_branch
  → 对应 run_manifest
  → 当前分支是否包含源码
  → 运行 preflight 或 dry-run
  → 最后才执行正式实验
~~~

如果某一步缺失，不要用另一个脚本“猜着重跑”；先把它记录为 provenance 缺口。
