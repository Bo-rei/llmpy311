# s2c 项目完整说明

## 1. 项目一句话概括

s2c 是一个用于开放意图识别的三层级联系统，核心目标不是单模型分类，而是在真实开放场景里同时做到：

- 识别已知意图。
- 拒识未知意图。
- 把已知意图分到正确领域。
- 在领域内完成细粒度意图分类。

如果一个人完全不了解这个项目，只看这一篇文档，应该能够知道：项目做什么、数据从哪里来、代码入口在哪里、当前做到了什么、哪里还不稳、下一步为什么要做某个消融。

## 2. 项目为什么存在

开放意图识别的核心难点不是“能不能分类”，而是“遇到训练集中没有的请求时，系统是否能先停下来”。

普通多分类模型面对开放场景时，常见问题是：

- 会把未知请求强行分到某个已知类。
- 在边界样本上过度自信。
- 单点 accuracy 看起来不错，但系统层面很脆。

这个项目就是围绕这个问题构建的。它把任务拆成三层：

1. Gate 先判断是否是 OOS。
2. Router 再决定属于哪个 domain。
3. Expert 最后做域内意图识别。

这样设计的原因很简单：开放场景本身就不是一个单一分类问题，而是一个“先拒识、再路由、再精分类”的系统问题。

## 3. 当前主线架构

### 3.1 Gate

Gate 是整个系统最重要的模块之一，职责是判断输入是不是已知意图。

当前主线不是传统单纯分类，而是几何门控 + score-based 决策。项目中出现过多种 gate 变体，但现阶段最重要的是明确：

- Gate 负责系统能不能成立。
- Gate 的错误会传导给后段所有模块。
- Gate 的收益和损耗，最终要在系统级指标里看，而不是只看 gate 自己的准确率。

### 3.2 Router

Router 负责把通过 Gate 的 ID 样本路由到对应的 domain。它不是 OOS 检测器，也不是最终意图分类器，而是一个中间决策层。

当前 Router 的单点表现已经很强，说明“把 ID 样本分到域里”这件事本身不是系统主要瓶颈。

### 3.3 Expert

每个 domain 都有自己的 Expert，负责域内细粒度意图识别。

当前项目里 Expert 的单点结果也比较稳定，说明单个 domain 的分类能力已基本足够。真正的问题不是 Expert 不会学，而是上游 Gate/Router 是否把样本正确地送到它面前。

### 3.4 Pipeline

Pipeline 是三个阶段串起来后的系统整体。这个项目最终必须看 pipeline 指标，因为只有 pipeline 能回答一个实际问题：用户发来一条句子，系统到底能不能正确拒识、正确路由、正确分类。

## 4. 项目当前的真实状态

### 4.1 数据已经锁定

项目当前唯一活跃数据版本是 `data/current -> v19`。这不是一个建议，而是实际执行口径。

### 4.2 训练与评估入口已经存在

关键入口包括：

- `tools/gate/train_multisphere_corrected.py`
- `tools/train/train_router_v19.py`
- `tools/eval/eval_system_pipeline_v19.py`
- `tools/analysis/run_pipeline_ablation_matrix_v19.py`
- `tools/analysis/run_prototype_gate_final_pipeline_v19.py`
- `tools/analysis/build_prototype_gate_anchored_summary_v19.py`

也就是说，项目不是“纸面方案”，而是已经有训练、评估、消融、结果汇总四条实际链路。

### 4.3 系统级 baseline 已经存在

当前可以作为主锚点的系统结果来自 `prototype_gate_chain_verify_2026-03-28` 下的 `full_pipeline_group2_ref`。

这个结果之所以重要，不是因为它最好看，而是因为它是当前最适合做后续消融对照的稳定参考点。

### 4.4 单点模型并不是瓶颈主体

Router 和 Expert 的单点结果都已经比较好。换句话说，这个项目不是“模型不够强”，而是“级联边界和门控策略还没完全收敛”。

## 5. 数据从哪里来

### 5.1 活跃版本

当前活跃数据版本为 `v19`，入口为 `data/current`。

### 5.2 数据分层

#### Gate 数据

Gate 数据用于判断 ID/OOS，当前审计显示规模为：

- train: 7500
- val: 3100
- test: 5499

#### Router 数据

Router 数据用于 domain 路由，关注的是 domain-level 预测与校准。

#### Expert 数据

Expert 按 domain 划分，每个 domain 都有独立 train/val/test。典型规模大约是：

- train: 800
- val: 160
- test: 240

### 5.3 数据审计结论

当前审计文件告诉我们的事实是：

- train_test_overlap = 0
- 在 max_length=128 下 tokenizer 零截断
- OOS 大多数是明显 outlier，只有一小部分是边界样本

这说明数据总体是干净的，项目主要不是“数据有大问题”，而是“边界样本怎么处理更合理”。

- `src/`：核心实现。

- `src/gate/`：OOS 检测、prototype gate、semantic gate 相关实现。

- `src/pipeline/`：把 Gate、Router、Expert 串起来的系统逻辑。

## 7. 当前实验结果说明了什么

### 7.1 系统级 baseline

当前最重要的系统级基线是：

- `macro_f1 = 0.801317`
- `known_acc = 0.784793`
- `oos_f1 = 0.901434`
- `gate_oos_rej = 0.908923`
- `gate_id_recall = 0.844375`

这说明系统已经能够工作，而且 OOS 检测效果是有意义的。但同时也说明：Gate 对已知样本的误杀仍然存在，系统还没有完全收敛。

### 7.2 无 Gate 会怎样

无 Gate 的对照结果明显更差，说明 Gate 不是装饰品，而是系统成立的前提。

### 7.3 Router 与 Expert 的单点表现

Router 的测试准确率在 95% 左右，Expert 的平均测试准确率在 93% 左右。也就是说，这两个模块单独看都不弱，所以系统误差主要不来自它们本身。

### 7.4 真正需要关注什么

真正要关注的是：

- Gate 如何在 ID 召回和 OOS 拒识之间找到更稳的边界。
- Gate 输出如何影响 Router 和 Expert。
- Decision policy 是否真的值得复杂化。

## 8. 为什么后续消融应该聚焦 Gate

因为当前已有结果已经说明：

1. Router 单点能力足够强。
2. Expert 单点能力也足够强。
3. 系统级损耗主要来自 Gate 和后段级联决策。

所以最有信息量的后续消融，不是继续做 gate family / prototype family / decision family 的大矩阵，而是围绕两条主线做结构化实验：

1. `Gate -> Router -> Expert` 三层结构是否必要。
2. `MiniLM` + `SmolLM` 这种异构骨干是否真的优于保持级联结构的纯 MiniLM 对照。

## 9. 当前主锚点是什么

当前主锚点是 `full_pipeline_group2_ref`。

它的作用不是“永远最好”，而是“当前最适合拿来做比较的稳定参考”。所有新实验都应该报告相对它的 delta，否则很难判断变化到底是改进还是漂移。

## 10. 为什么现在不能继续写成空泛的项目介绍

因为项目已经进入结果驱动阶段。陌生读者需要的不是“我们做了一个很厉害的系统”这种空话，而是下面这些具体事实：

- 数据版本是什么。

- 哪个模块做什么。
- 结果文件在哪里。
- 当前最强基线是什么。

如果这些信息不写清楚，文档就不能算“项目完整说明”。

## 11. 目前最重要的结论

1. 这个项目的核心不是单点分类，而是开放场景中的级联系统。
2. 数据已经定型，当前问题主要在边界样本与门控策略。
3. Router 和 Expert 已经不再是主矛盾。
4. Gate 是系统必要组件。
5. 后续最合理的实验是结构必要性 + 异构骨干消融。

## 12. 下一步最合理的动作

如果只允许做一件最有价值的事，应该是：

1. 固定 `full_pipeline_group2_ref` 作为系统主锚点。
2. 用 `validate_router_confidence_threshold_v19.py` 先把 `no_gate_confidence` 的阈值锁死在 validation-only。
3. 运行 `run_structure_backbone_ablation_v19.py`，得到 `full_pipeline_group2_ref`、`no_gate_confidence`、`single_stage_minilm`、`single_stage_smollm`、`cascade_minilm` 的对照结果。
4. 把结论写成可回放、可审计、可复算的结果包。

这才是一个陌生读者看完就能真正理解项目的文档。
